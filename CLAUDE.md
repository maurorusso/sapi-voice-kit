# sapi-voice-kit — project context

## The goal

Let someone interact with Claude Code by voice: type or dictate a prompt, and instead of reading the answer on screen, hear it — the *complete* content of the response, rephrased so it's clear and natural when heard, not a mechanical truncation and not an ultra-short summary. Built for anyone who'd rather listen than read on screen.

Two things that follow from that goal, and that any change should keep true:
- The full written response on screen must stay exactly as generated — nothing added, nothing removed, nothing hidden in it. The voice mechanism is entirely separate from what's displayed.
- What gets read must be a faithful, complete spoken rendering of the answer — the way a person would read the answer aloud and put it in their own words, not a shortened stand-in for it (except in `summary` mode, which exists specifically for when a condensed version is wanted).

Native Windows `System.Speech` (SAPI) — no API keys, no Python, no installer.

## The four reading modes

The `Stop` hook receives the turn's `last_assistant_message` as JSON on stdin and decides what to speak based on `config.json`'s `mode` field:

- **natural (default):** the complete response, cleaned of markdown (headings, bullets, links, code syntax), spoken instantly. Nothing shortened.
- **literal:** the complete response exactly as written, no cleanup at all.
- **summary:** an actual condensed summary via a separate `claude -p --safe-mode --model haiku` call. Opt-in, not the default, because that call reliably costs ~20s of dead silence regardless of response length. Falls back to natural mode if the call fails for any reason.
- **active:** the model speaks for itself, mid-turn, by piping a short paraphrase to `say.ps1` — no waiting on a separate call; in this mode the `Stop` hook does nothing (it would otherwise produce overlapping audio). This works the same way conceptually in the CLI and in Claude Cowork/Desktop, just over two different transports depending on which one is actually running, since Cowork doesn't fire plugin hooks at all (confirmed against multiple open `anthropics/claude-code` issues):
  - **CLI:** a `UserPromptSubmit` hook (`prompt-active-mode.ps1`) reminds the model every turn to pipe its paraphrase to `say.ps1` via stdin. Since this has the model run a command itself, Claude Code will ask for a one-time permission the first time in a session — a plugin cannot pre-grant its own permissions, and shouldn't be able to.
  - **Cowork/Desktop:** this plugin declares a local MCP server (`.mcp.json` → `mcp-server/server.js`) exposing one tool, `read_aloud`, which pipes its `text` argument to `say.ps1` exactly like the CLI's heredoc does - same script, same mutex, same pronunciation dictionary. `skills/cowork/SKILL.md` reminds the model to call it each turn (and explicitly only applies when running as Cowork, not the CLI, to avoid double-triggering), since Cowork has no `UserPromptSubmit`-equivalent to force that reminder the way the CLI does - a real reliability downgrade from the CLI path, documented here, not hidden.

In natural, summary, and active modes, common programming terms (git, commit, config, hook, function, ~100 total) are read with correct pronunciation via `PromptBuilder.AppendTextWithPronunciation` (real IPA phonemes) on the *same* selected voice, rather than switching to a second voice (tried and rejected — it works, but sounds like two people talking and roughly doubles speaking time on code-heavy responses). Most entries use standard English IPA; a few loanwords are deliberately "castellanizado" (a plain Spanish vowel) instead, when that's what actually sounded right by ear - see the design note on `$script:TechPronunciations` in common.ps1.

Run `/sapi-voice-kit:test` (`scripts/say-test.ps1`) after touching any of this - it speaks one fixed sentence covering every cleanup/pronunciation rule at once (dictionary terms, dotfiles plain and in backticks, full paths, URLs, abbreviations including the two that previously broke on real names, a question, an unpunctuated line break, a bullet list), so a regression shows up by ear immediately instead of needing a new throwaway test script written from scratch.

Voice/language is auto-detected from the installed voice matching the system language (`Get-Culture`), with a manual override stored in `config.json` inside the plugin's persistent data directory, so it survives plugin updates.

## Muting and on-demand reading

Two controls independent of the four modes above:

- **`muted` flag** (`/sapi-voice-kit:mute on`/`off`): a pause, separate from `mode` so toggling it doesn't lose the chosen mode. Checked first thing in `speak.ps1`, `say.ps1`, and `prompt-active-mode.ps1`, before any other logic. **Update:** this used to be machine-wide (one flat shared `config.json`, no notion of environment) - since the `local`/`cowork` namespace split (see the design note further down), muting is per-environment: muting from the CLI/Code tab doesn't mute Cowork, and vice versa. Still shared *within* `local` (CLI and Desktop's Code tab can't be told apart, so they share one mute state), just no longer shared with Cowork.
- **`read-last` skill**: lets the user ask, in the current turn, to have a specific response read aloud right now ("leeme eso") regardless of mode or mute state. Reuses `say.ps1`'s stdin-heredoc mechanism (same one active mode uses) with a `-Force` switch that bypasses the mute check — an explicit request should still work while muted. Unlike the other skills, this one is model-invocable (no `disable-model-invocation`), since it's meant to be triggered by natural language, not just the slash command. Writes nothing to disk: the text being read is already in the conversation's context when this runs.

## Design notes for contributors

- **Marker-in-response approach, rejected:** an earlier version had the model append a `<!--voice ... -->` block to its own response, extracted by the `Stop` hook. It worked, but showed up as literal visible text on screen — a hook only ever sees exactly what was already shown to the user, there's no hidden channel. Replaced by local text cleanup (no model cooperation needed) plus, later, the `active` mode above for when a model-authored version is actually wanted.
- **`AppendTextWithPronunciation` needs real IPA.** The pronunciation-hint parameter must be concatenated IPA Unicode characters with no spaces (Microsoft's documented example: `"duˈbwɑ"`) — space-separated ASCII approximations fail with an "invalid phoneme" error.
- **Encoding pitfalls on Windows/PowerShell 5.1, twice:** `[Console]::In.ReadToEnd()` and `[Console]::OutputEncoding` both default to the console's OEM codepage for redirected streams, not UTF-8 — corrupting accented characters on the way in (reading the hook's stdin) and on the way out (capturing `claude -p`'s output). Fixed by reading/writing raw bytes and decoding explicitly as UTF-8 in both directions. Separately, `.ps1` files need a UTF-8 BOM or PowerShell 5.1 misreads non-ASCII literals written directly in the source.
- **Command injection in a model-constructed shell command.** An early version of the `active`-mode instruction told the model to run `printf '%s' "PARAPHRASE" | powershell ...` with its own paraphrase substituted into a double-quoted string — a real risk, since a paraphrase mentioning shell syntax (`$(...)`, backticks, quotes) would have it evaluated by the shell. Fixed by using a heredoc with a single-quoted delimiter (`<<'EOF'`) instead, which passes the body through with zero shell expansion regardless of content.
- **Cross-process speech overlap, observed live.** Two parallel Claude Code sessions with this plugin active could speak at the same time — each process owns its own `SpeechSynthesizer` with no knowledge of any other process, so simultaneous speech overlapped on the shared audio device and was unintelligible. Fixed with a named Windows Mutex (`Local\SapiVoiceKitSpeak` — session-scoped, not `Global\`: the real scenario never crosses a Windows session boundary, and `Global\` would need a privilege a restricted or Remote-Desktop-session user might not have) around the actual `Speak()` call in `Invoke-SpeechSynthesis`, shared by every caller — processes now take turns instead of talking over each other. A 60s `WaitOne` timeout keeps a crashed or unusually slow holder from permanently silencing everyone else.
- **Spanish question intonation: investigated, no fix found, documented as a known limitation.** Questions ("¿...?") read with weak or no rising interrogative intonation - confirmed this is NOT something this plugin's code causes: a raw `Speak()` call with zero processing already sounds this way. Tried and rejected: SSML `<prosody pitch="+X%">` over the whole sentence (inconsistent - helped some questions, made others sound like statements), pitch boost scoped to only the final word(s) (same inconsistency), SSML `<prosody contour="...">` drawing a rise over just the last word or the end of the sentence (ignored entirely - three variants, plain vs. contour on the last word vs. contour over the whole sentence, sounded identical side by side), and switching to a modern OneCore voice (`Windows.Media.SpeechSynthesis`, confirmed reachable from Windows PowerShell 5.1 and audibly different from the SAPI5 Desktop voice) - Pablo (OneCore) showed the identical lack of question intonation as Helena Desktop, side by side, same text. Followed up later with SSML `<prosody contour="...">`/`pitch="+40%"` directly against a OneCore voice (Pablo) via `SpeechSynthesizer.SynthesizeSsmlToStreamAsync` - same non-result, confirmed live: a plain question, a contour rising only on the last word, a flat `+40%` pitch boost, and a contour over the whole sentence all sounded identical, no interrogative rise on any of them. Conclusion: neither legacy SAPI5 nor modern OneCore Microsoft Spanish voices reliably produce natural interrogative prosody, and neither responds to SSML pitch/contour markup for it either - this is a real limitation of "100% native Windows TTS, no API keys," not a bug to chase further with this voice family. A neural TTS engine (ElevenLabs, Azure Neural, etc.) would likely handle this correctly, at the cost of the API-key/external-dependency tradeoff this project exists specifically to avoid.
- **A OneCore voice is now preferred by default over SAPI5 - prototyped and paused once, then finished after the rate-control blocker turned out to have a real fix.** A live side-by-side listening test confirmed OneCore's Pablo sounds clearly more natural overall than the SAPI5 Desktop voices this plugin used exclusively before, and that the same `$script:TechPronunciations` IPA dictionary carries over correctly via SSML `<phoneme alphabet='ipa'>` instead of `PromptBuilder.AppendTextWithPronunciation` - confirmed live, word by word, once the prototype correctly wrapped every dictionary word present in the test sentence (an early version missed wrapping `json`/`github`, which made them sound *worse* on OneCore and was mistaken for a voice problem before the gap was found). First attempt hit two real problems once rate control was tested: SSML `<prosody rate="N%">` had no audible effect on this voice at all (consistent with the pitch/contour finding above - this voice broadly ignores prosody markup), and an unconfirmed echo artifact - paused rather than shipped broken. Picked back up later: the rate problem had a real fix, not just a workaround - `Windows.Media.SpeechSynthesis.SpeechSynthesizer.Options.SpeakingRate` is a distinct native property (not SSML at all), confirmed live to actually change speed correctly where the SSML attribute did nothing. The echo turned out to not reproduce with normal single-utterance pacing (one utterance with `player.Dispose()`/`netStream.Dispose()` after each `PlaySync()`, not three rapid calls in a row like the original test) - never confirmed as a real engine bug, most likely just overlapping playback from that rapid-fire test pattern.
  - `Resolve-SpeechTarget` (common.ps1) picks the engine: an explicit `/sapi-voice-kit:voice` override is checked against both engines by name first (OneCore `DisplayName`s like "Microsoft Pablo" and SAPI5 `Name`s like "Microsoft Pablo Desktop" never collide, so a `voiceName` saved before this existed still resolves the same way it always did); otherwise, auto-detection now prefers a OneCore voice matching the target language, falling back to the SAPI5 auto-detect this project always used when none exists for that language - OneCore's natural voices need Windows 11 22H2+ and a one-time download from Settings → Narrator → "Agregar voces naturales", never assumed present.
  - `ConvertTo-OneCoreSsml` builds the phoneme-wrapped SSML (tokenize-once, O(1) dictionary lookup per token, same approach as `Get-PronunciationPrompt` and for the same reason), `Invoke-OneCoreSpeech` sets `Options.SpeakingRate` (mapped from SAPI5's -10..10 `rate` config field with the same roughly-doubles-per-10-units curve SAPI5's own `Rate` property uses) and calls `SynthesizeSsmlToStreamAsync`, playing the result with `SoundPlayer` - all still going through the same cross-process mutex as SAPI5 always did, and falling back to SAPI5 for that one utterance if OneCore throws for any reason.
  - `list-voices.ps1` now lists both engines' voices in one table (labeled by engine, since names never collide) and prints which one is actually active.
- **The /ʃ/ ("sh") phoneme isn't well supported by this voice - "push" reads as "pus," and that's the best available option.** Confirmed live across four phoneme spellings (`pʊʃ`, the affricate `pʊtʃ`, without the short u, and a doubled `ʃʃ`) - all four came out sounding identical, all missing the "sh" sound. This isn't a spelling problem: this voice's phone inventory appears to fall back to a plain /s/ for this IPA symbol regardless of how it's written. Confirmed the current entry is still worth keeping anyway: the same word with no pronunciation hint at all sounds worse, not better. `function` uses the same phoneme mid-word and likely has the same limitation - not worth a special case for one imperfect-but-still-better-than-nothing sound.
- **Raw URLs read as the wrong thing entirely, not just badly.** A plain `https://...` link spoken aloud came out announcing an emoticon instead of a link - `https://` starts with a colon immediately followed by a slash, and some TTS text normalization recognizes `:/` as the "confused/displeased face" emoticon before it ever gets far enough to recognize a URL. Fixed the same two ways as the file-extension problem: `ConvertTo-SpokenUrls` (common.ps1) replaces any bare `https?://\S+` with "el link" for natural/literal and as a fallback in say.ps1, and summary/active/read-last's prompts tell the model to refer to a link naturally instead of writing it out. The screen still shows the exact URL untouched either way - same principle as markdown links, which already only speak the label, never the address.
- **Full paths, same call as URLs: collapse instead of reading raw.** A path read character-by-character (drive letter, every backslash, every folder) isn't useful spoken, and risked the same kind of TTS misreading URLs did. `ConvertTo-SpokenFileNames`'s regex now consumes any leading path segments too, so `C:\...\common.ps1` or `scripts/common.ps1` collapse to `common punto ps1`, not just bare `common.ps1`. `ConvertTo-SpokenPaths` catches the rest - a bare folder mention with no recognized extension - scoped to drive-letter-absolute paths specifically (`C:\...`), an unambiguous signal in prose with essentially no false-positive risk. Researched first: no single canonical rule exists for reading paths aloud across TTS engines - the consistent pattern is each engine building its own domain-specific normalization rather than relying on default parsing, which is the approach already used throughout this file.
- **File names read oddly, fixed two different ways for two different kinds of mode.** `common.ps1` (a raw dot before a file extension) got read as an odd swallowed pause instead of sounding like a name. For the mechanical modes (natural/literal's cleanup has no model in the loop), fixed with a regex in `Get-CleanedText` that rewrites `word.extension` (for a maintained list of known extensions) into `word punto extension`. For the modes that go through the model (`summary`'s prompt, `active`'s per-turn instruction, `read-last`'s instructions), fixed instead by telling the model directly to write "punto"/"dot" instead of a literal period — since that text is never shown on screen, there's no cost to writing it however sounds best spoken.
- **Cowork support went through a real, discarded first attempt - reusing Cowork's own shell tool - before landing on a local MCP server.** The first design had a skill tell the model to run `say.ps1` via Cowork's own workspace shell tool (`mcp__workspace__bash`), reasoning it was equivalent to the CLI's `Bash` tool. Wrong, confirmed live by Cowork itself: "Mi shell es una máquina Linux en la nube, no tiene PowerShell ni parlantes" - that tool runs in a remote cloud sandbox with zero access to the user's actual machine. A local MCP server (`.mcp.json` → `mcp-server/server.js`) was the correct mechanism all along - confirmed live afterward with a disposable test server (`plans/*.md`, gitignored, never part of the plugin) registered via Cowork's own Settings → Developer → local MCP servers panel: real audio, in both a Code session and an actual Cowork session, permission-prompted on first call the same way `active` mode is in the CLI. Only then was the real `read_aloud` tool built.
- **Cowork support first shipped as a separate `cowork` mode value, then was collapsed into `active` after a code review surfaced the duplication.** The first cut of this feature added `cowork` as a fifth mode string, parallel to `active` - its own `ValidateSet` entry, its own no-op branch in the `Stop` hook, its own step in `skills/mode/SKILL.md`. A multi-angle review (correctness/reuse/altitude passes) independently converged on the same point from different directions: `active` and `cowork` are the same underlying behavior (the model speaks a short paraphrase itself, mid-turn) differing only in *which transport* the running client supports, so modeling them as two mode values meant three-plus places independently tracking "is cowork active" with no shared source of truth - exactly the kind of duplication that already caused one real bug (the config.json BOM issue). Collapsed to one `active` mode: the CLI's hook and Cowork's skill both gate on the same `mode == 'active'` value, and `skills/cowork/SKILL.md` explicitly checks "am I running as Cowork, not the CLI" (the model already knows which client it's in) instead of relying on a mode-string difference to avoid double-speaking.
- **Collapsing to one `active` mode traded a rare double-speak risk for a real one, caught by a follow-up review.** Before the merge, `mode == 'cowork'` itself filtered out the CLI (a CLI user would basically never set it), so a CLI session invoking the Cowork skill by mistake was already unlikely. After the merge, `mode == 'active'` is equally likely from either client, so nothing but the skill's own advisory "you're the CLI, do nothing" instruction stands between a CLI session's hook-driven heredoc and the model *also* invoking `skills/cowork/SKILL.md` and calling `read_aloud` in the same turn - `.mcp.json` registers that tool for any session, CLI included, not just Cowork. Fixed at the one point both paths already share: `say.ps1` (called directly by the CLI heredoc, and by `mcp-server/server.js`'s `speak()`) now checks `Test-RecentActiveSpeech`/`Set-RecentSpeechMarker` (common.ps1) - a bare timestamp in the plugin's data folder, not the spoken text itself. Originally hashed the text too (only flag it as a duplicate if it matched exactly), but review found that defeated the guard's own purpose: the CLI and Cowork paths each get an independently-written paraphrase of the same response, so they're very unlikely to be byte-identical - switched to a time-only window instead. Skipped whenever `-Force` is set, in both directions: an intentional repeat ("leeme eso" twice) is never swallowed, and it never updates the marker either, so it can't cause the *next* real turn to be wrongly treated as a duplicate of it.
- **The MCP server is hand-rolled JSON-RPC, not the official `@modelcontextprotocol/sdk`.** That SDK is an npm package - pulling it in means either an `npm install` step somewhere (breaks "no installers") or vendoring compiled output into the repo. The protocol surface actually needed (`initialize`, `tools/list`, `tools/call`, one tool) is small enough that hand-rolling it was the smaller trade-off, and it was validated working end-to-end (not just assumed) with the disposable test server before writing the real one.
- **No temp files, anywhere, in any mode.** Text that gets spoken always travels through memory (stdin/stdout between processes) — never through an intermediate file, not even a briefly self-deleted one. Considered and deliberately rejected in favor of not writing anything in the first place.
- **Debug logging is opt-in and bounded.** With `/sapi-voice-kit:debug` off (the default), nothing *readable* is written to the plugin's data folder beyond the settings a user explicitly changes — no logs, no copy of what was spoken. The one exception: `active` mode's double-speak guard (see below) writes a bare timestamp to `.last-active-speech` on every non-forced speech, regardless of the debug setting - not a privacy exception (there's no spoken content in it, just a number), but worth naming here explicitly so this line stays accurate. When debug logging is turned on for troubleshooting, each log file is capped (trimmed to the last 200 lines once it exceeds ~50KB) so it never grows unbounded.
- **`git push`/plugin-install SSL errors on Windows behind an antivirus that does HTTPS interception:** fixed with `git config --global http.sslBackend schannel`, which makes git use the Windows certificate store (which trusts the antivirus's injected cert) instead of git's own bundled one.
- **Abbreviations, dotfiles, and unpunctuated line breaks, fixed with the same "mechanical regex for natural/literal, direct instruction for the model-driven modes" split already used for file names.** `ConvertTo-SpokenAbbreviations` (common.ps1) expands common abbreviations ("etc." → "etcétera", sourced against the RAE's own official list for the Spanish entries) instead of letting them get spelled out letter by letter. `ConvertTo-SpokenDotfiles` handles a leading-dot file name (`.env`, `.mcp.json`) separately from `ConvertTo-SpokenFileNames` - that function requires a non-empty name *before* the dot it matches, so a bare leading dot had nothing to match and fell straight through untouched, or partially matched and left a stray dot (confirmed live before the fix). `Add-ImplicitLineEndPeriods` treats any line break not already ending in real punctuation as if it had a period - markdown/plain text often wraps a paragraph onto a new line with nothing marking the boundary, which otherwise reads as one run-on sentence.
- **Pronunciation dictionary expanded with proper nouns/loanwords (readme, npm, node, javascript, mcp, claude, etc.), tuned live word by word, not assumed correct from the transcription alone.** Two patterns emerged from that listening pass, both now applied as a standing rule for new entries: (1) a monosyllabic word needs an explicit stress mark (`ˈ`) even though there's only one syllable to stress - without it, words like "app" and "skill" came out clipped/underpowered, confirmed by A/B listening. Retrofitted to the original 82-entry dictionary too, not just new entries. (2) Some loanwords sound better "castellanizado" - a plain Spanish vowel instead of the closer-to-native English diphthong - specifically confirmed for `prompt` (plain "o", not the ɔ/oʊ that sounded "floja"/"like an -ou-") and `localhost`/`model` (same). This is NOT a blanket rule: `node`, using the same oʊ diphthong as the "wrong"-sounding `local`, was confirmed to already sound fine and was deliberately left alone - each entry gets judged on its own, not pattern-matched from a neighbor.

## Distribution

A single repo acting as both the plugin and its own marketplace is the standard pattern for an individual Claude Code plugin. End-user install:

```
/plugin marketplace add <owner>/sapi-voice-kit
/plugin install sapi-voice-kit
```

Use the full `https://github.com/<owner>/sapi-voice-kit` URL rather than the `owner/repo` shorthand — the shorthand makes Claude Code default to an SSH clone, which fails on machines without SSH access to GitHub configured.

Not using a curl/irm-style installer script: it's not the native distribution mechanism for Claude Code plugins, and piping a remote script into a shell is a pattern worth avoiding regardless.

**A user-uploaded plugin's bundled `.mcp.json` server does NOT auto-register in an actual Cowork session - a real, documented platform limitation, not something fixable from this plugin's side.** Confirmed live: the plugin installs correctly via Cowork's own "Upload plugin" flow (skills and slash commands work, `/sapi-voice-kit:test` gets recognized), but `read_aloud` never appears under Configuración → Desarrollador → Servidores MCP locales, unlike Claude Desktop's "Code" tab, where the exact same package auto-registers the same server (also confirmed live, same session). Root cause found in Anthropic's own docs (`claude.com/docs/cowork/3p/extensions`): the "User extensions" section says a self-uploaded plugin "can bundle skills, hooks, slash commands, and sub-agents" - MCP servers are conspicuously absent from that list - while `.mcp.json` bundling is documented only under "Organization plugins (admin)", an admin-provisioned distribution path this project (an individual open-source tool, not an org deployment) doesn't use. Tried and reverted: adding `"mcpServers": "./.mcp.json"` to `.claude-plugin/plugin.json` on the theory Cowork needed an explicit manifest reference - didn't fix it, and isn't a documented field anyway (the real inline-object form, `"mcpServers": {"name": {...}}`, is a *different*, separately-known-buggy CLI feature per anthropics/claude-code#16143 - unrelated to this). The only current workaround for a Cowork user is the same one-time manual registration (Settings → Developer → Local MCP servers → Edit configuration) this project validated earlier with a disposable test server - documented in the README's "Uso en Claude Cowork" section, not silently glossed over. CLI and Desktop's Code tab remain fully automatic; this gap is Cowork-specific.

**A standalone `.mcpb` (Desktop Extension) was researched as a possible fix for the above and confirmed to be a dead end - not attempted, on purpose, once the research made clear it would hit the identical wall.** The theory was that packaging `mcp-server/server.js` as its own MCPB bundle (a format separate from a Claude Code plugin, installed via Claude Desktop's own Settings → Extensions, `github.com/modelcontextprotocol/mcpb`) might get bridged into Cowork automatically where the plugin-bundled `.mcp.json` above doesn't. Research (not a live test) found a tracked, still-open Anthropic issue, `anthropics/claude-code#26259`, showing the Cowork VM's process spawner builds its `--mcp-config` argument from only `"type": "sdk"` servers and silently drops any stdio-transport server - including Desktop Extensions installed via the Extensions UI - even when Claude Desktop's own session metadata lists them as enabled. That's the same transport type `mcp-server/server.js` uses (a spawned Node child process talking stdio), so a `.mcpb` package of it would hit this exact bug, not route around it - repackaging changes the install screen, not the transport. The manual "Local MCP servers" JSON registration this project already documents is, per the same research, the mechanism that *does* get bridged into Cowork (it registers as `type: sdk` on Desktop's side) - so that existing workaround is already the correct one, not a stopgap waiting to be replaced by a `.mcpb`. Revisit this only if `#26259` gets fixed upstream, or if this project ever wants the heavier alternative that research also surfaced: wrapping `say.ps1`'s stdio server in an HTTP shim (e.g. `supergateway`) as a persistent local server, which sidesteps the stdio-vs-sdk distinction entirely at the cost of a always-running process instead of a spawned-per-call one - decided against for now, since Cowork is a secondary environment for this plugin.

**Update, contradicting the "never auto-registers" finding above: a later real test found the MCP server DOES sometimes auto-register in Cowork when installed from the marketplace.** Installing via Configuración → Plugins → Agregar marketplace, then installing the plugin itself, produced a working `read_aloud`-family tool with no manual step. Not reconciled with the earlier confirmed-negative test above - possibly a platform fix landed between the two tests, possibly it depends on install path (marketplace vs. "Upload plugin", which is what the original negative test used). The manual registration in the README stays documented as a fallback either way, with an explicit warning not to add both (it duplicates the server if the automatic one already registered).

**Config went from per-install, to one flat shared file, to two namespaces - each step driven by a real problem the previous step caused, not by planning ahead.** Originally, `config.json` lived inside whatever `${CLAUDE_PLUGIN_DATA}` a given install (CLI, Desktop's Code tab, Cowork) happened to be handed - confirmed live as a real bug: `/sapi-voice-kit:mode active` set from Code left Cowork's `read_aloud` still reporting "not configured in active mode," because Cowork was reading a config.json Code's install never touched. First fix: `Resolve-SharedDataDir` (common.ps1) redirected every install to one fixed shared file (`%USERPROFILE%\.claude\plugins\data\sapi-voice-kit-shared\config.json`), with one-time migration and cleanup of the old per-install files. This fixed the bug, but flattened away something a user had liked without realizing it: a different voice in Cowork than in the CLI, which the old (accidentally divergent) per-install configs happened to give them for free. Asked directly to bring that back, and told plainly that CLI and Desktop's Code tab are **structurally indistinguishable** to this plugin (identical hook mechanism, no environment signal exists to tell them apart - confirmed, not assumed), landed on two namespaces inside the one shared file instead of a fully flat one: `local` (CLI + Code tab, forced together by that same hard limit) and `cowork` (everything reaching this plugin through the MCP tools in `mcp-server/server.js`, which is unambiguous - Cowork's own shell has no PowerShell and can only get here via MCP). `Get-VoiceConfig`/`Save-VoiceConfig` (common.ps1) take a `-Namespace` param, default `'local'`, threaded through every `.ps1` script; `mcp-server/server.js` passes `-Namespace cowork` to every script it spawns, and its own `readConfiguredMode()` reads `config.cowork.mode` directly. The active-mode double-speak guard (`Test-RecentActiveSpeech`/`Set-RecentSpeechMarker`) deliberately stayed **non-namespaced** through all of this - its whole job is deduplicating speech *across* environments in the same turn, so namespacing it would have defeated it.

**The shared-dir migration/cleanup had a real data-loss bug, caught by this project's own tests before it shipped, not found live by a user.** The cleanup step (deleting a per-install's old `config.json` and log files once no longer needed) originally ran unconditionally on every call, gated only on `$PluginData -ne $shared`. That's wrong whenever the shared directory already exists because a *different* install migrated first: this install's own `config.json` was never copied anywhere by that earlier call, yet the unconditional cleanup deleted it anyway on this install's very next run - silently discarding settings that were never migrated, not just leftover tidiness. Reproduced deliberately (one fake install's config.json wiped, verified via a live before/after read) before fixing it. Fixed by tracking whether *this specific call* just finished copying `config.json` into the shared file (`$configMigratedThisCall`) and only deleting the old `config.json` when that's true or it never existed - the other per-install files (the double-speak marker, debug logs, last-spoken-text) never hold settings worth preserving, so those stay unconditionally safe to clean up. Trade-off, accepted on purpose: an install that's never "first" to touch a fresh shared directory keeps its own now-orphaned `config.json` sitting unused in its old folder forever rather than risk deleting un-migrated data - correctness over full tidiness.

**Follow-up, found by a multi-angle code review of the namespace redesign, not live: two real races, both closed with one new cross-process mutex.** (1) The first-ever migration had a TOCTOU window - two processes starting up close together (e.g. the CLI's first hook and Cowork's MCP server around the same time) could both observe the shared directory as "doesn't exist yet" and both attempt migration, the second one's plain overwrite silently discarding the first's. (2) `Save-VoiceConfig`'s read-whole-file/modify/write-whole-file cycle had no lock at all - now that `local` and `cowork` live in one shared file instead of separate per-install ones, two near-simultaneous writes (even to *different* namespaces) could race, with the second writer's full-file snapshot overwriting the first's change. Fixed both with `Invoke-WithConfigLock` (common.ps1), a named Windows Mutex (`Local\SapiVoiceKitConfig`) modeled directly on the pre-existing `Local\SapiVoiceKitSpeak` audio mutex (same file) - same `Local\` reasoning (never crosses a Windows session boundary, so no elevated privilege needed), same "proceed anyway on timeout rather than go silent" stance, just a much shorter timeout (5s vs. 60s) since config I/O takes milliseconds, not however long speech synthesis takes. The migration's own completion check also moved from "does the shared directory exist" to "does the shared file's `local` key exist" - both more precise (a Cowork-only call could have created the shared file first without ever touching `local`) and now race-safe, since it's checked under the same lock. While fixing this, the migration's hand-rolled JSON read/write was also replaced with the same `Read-ConfigRoot`/`Write-ConfigRoot` helpers `Save-VoiceConfig` uses (a reviewer flagged the duplication as a drift risk - two independent serializers for the same file shape) - one code review's efficiency, simplification, and altitude angles all separately flagged `Resolve-SharedDataDir`'s cleanup work re-running on every call within a process too (3-4 times per single `say.ps1` invocation, all but the first a guaranteed no-op); fixed with a `$script:SharedDataDirCleanupDone` per-process memoization flag.

**Security review of the same redesign: zero findings.** Explicitly checked and ruled out: command injection (every `spawn('powershell', args)` call in `mcp-server/server.js` uses the array form, never `shell: true` or string concatenation - confirmed live that a crafted flag-like value passed as a tool argument doesn't get reinterpreted as a different PowerShell parameter, it just fails to bind and the script exits non-zero), path traversal (the shared directory is built only from `$env:USERPROFILE`/`os.homedir()` plus fixed literals, nothing tool-call-controlled reaches a path segment), and unsafe deserialization (every `ConvertFrom-Json`/`JSON.parse` on `config.json` is wrapped in try/catch with a safe fallback - a malformed file degrades to defaults, nothing more).
